# __PROJECT__ — 项目工程目录

电动工具 / 电机控制类「硬件 + 固件」项目的标准目录骨架。新项目立项时整棵复制，改个项目名即可。

顶层编号表示**项目生命周期顺序**：

> 输入 → 设计 → 硬件 → 固件 → 报告 → 交付 → 管理

目录名除 `03_software/` 内部（沿用 Keil/Git 工具链习惯）外一律用中文，便于人读。

---

## 一、目录总览

| 目录 | 放什么 | 性质 | 只读 |
|---|---|---|---|
| `00_input/` | 立项阶段拿到的**原始输入**资料，不论来自客户、供应商还是内部 | 原始信息，不加工 | ★ 只读 |
| `01_docs/` | 我方产出的**设计文档**：需求、方案、接口、参数标定 | 设计输出 | 可改 |
| `02_hardware/` | 原理图、PCB、BOM、结构、认证、打样记录 | 硬件产物 | 可改 |
| `03_software/` | 固件参考代码、单测、主工程、归档 | 固件产物 · **独立仓库** | 可改 |
| `04_report/` | **验证结果**：测试、评审、验证、标定记录 | 做完之后测出来的 | 可改 |
| `05_output/` | 交出去的**最终交付物**：固件、量产资料、用户手册 | 对外交付 | 可改 |
| `06_management/` | 计划、风险、变更、问题、会议、开发日志 | 过程管理 | 可改 |

> `01_docs` 与 `04_report` 的区别：前者是**做之前/做的过程中**写的设计意图，后者是**做完之后**测出来的数据与结论。
> `04_report` 与 `05_output` 的区别：前者是**自己看的**验证证据，后者是**给别人的**交付物。

### 关于 `03_software/`：固件用独立仓库

固件代码**不进本仓库**。根目录 `.gitignore` 里 `/03_software/**` 那一段把它整个排除了；
本仓库只保留 `03_software/` 的目录骨架（各子目录的 `.gitkeep`）和它自己的 `.gitignore`。

新项目里这样把固件仓库起起来：

```bash
cd 03_software
git init
git add .
git commit -m "固件仓库初始化"
git remote add origin <固件仓库地址>
```

这样做的好处：

- 固件有自己的提交历史和发布节奏，不会把硬件/文档仓库的 log 冲得看不清
- 固件仓库可以单独设为**私有**——模板仓库可以公开，固件不必跟着公开
- 往 `03_software/` 里放代码、改代码，根仓库的 `git status` 一律看不见，不会互相干扰

> ⚠️ 根目录的 `.gitignore` **不会继承**到 `03_software/`。
> Keil 中间产物（`Objects/`、`Listings/`、`*.uvguix.*` 等）的忽略规则写在
> `03_software/.gitignore`，那边才是生效的地方。

## 二、命名规范

### 1. 版本号 + 日期

凡是会迭代的产物，命名统一为 `Vx.x_YYYYMMDD`：

```
02_hardware/PCB/V1.0_20260310/
02_hardware/打样记录/V1.1_20260405/
05_output/固件_bin/固件_V2.3_20260710.bin
```

不允许出现「最终版」「真的最终版」「v2_确认版」「新建文件夹」这类命名。

### 2. 版本化文档：文件夹 + 版本文件 + 版本索引

`01_docs/`（以及 `06_management/项目计划`、`风险登记`）下每个文档**占一个文件夹**，
文件夹内放各版本文件与一份 `版本索引.md`：

```
01_docs/需求规格说明书/
├── 版本索引.md                            # 版本表 + 标明现行版本
├── 需求规格说明书_V1.0_20260910.md
└── 需求规格说明书_V1.1_20260920.md
```

规则：**新版本另存新文件，历史版本不删除、不覆盖**；每次新增版本，在 `版本索引.md` 上加一行并更新「现行版本」。
需要拿着旧版本对账时（客户确认过哪一版、打样按哪一版做的），翻索引即可。

### 3. 编号只给会持续增长的目录

`03_software/01_reference`、`02_hardware/PCB/V1.0_20260310` 这类会一直加新条目的目录才编号；
普通子目录用中文名不带序号，避免插新目录时被迫重排编号。

## 三、项目过程记录放哪里

原则：**按性质分散归档，用一条时间线串起来**。不要建一个「过程记录」大杂烩目录——三个月后没人翻得动。

| 过程记录 | 去哪 | 形态 |
|---|---|---|
| 与客户/供应商的沟通 | `00_input/沟通记录/` | 原始邮件、会议纪要、聊天导出，按 `YYYYMMDD_对方_主题` 命名 |
| 我方内部会议 | `06_management/会议记录/` | `YYYYMMDD_议题.md` |
| 设计变更（改了什么、为什么） | `06_management/变更记录_ECN/` | `ECN-001_变更标题.md`，一变更一文件 |
| 打样（Gerber、板厂、回样实测） | `02_hardware/打样记录/Vx.x_YYYYMMDD/` | 每轮一个目录 |
| 问题 / 缺陷 / 异常 | `06_management/问题追踪/` | `问题-001_标题.md`，带状态与责任人；总表见 `问题追踪表.md` |
| 标定调参过程数据 | `04_report/标定记录/` | 与最终参数分开，过程数据留痕 |
| **上面所有事的时间线** | `06_management/开发日志/YYYY-MM.md` | 按月一个文件，一条一行，摘要 + 链接 |

### 开发日志怎么写

`06_management/开发日志/` 下按月建文件（`2026-09.md`、`2026-10.md`……），每条只写**一行**，
指向上面某个具体文件。它是索引，不是正文——正文永远在各自的归档目录里。

```markdown
## 2026-09-24
- [沟通] 客户确认灯组件线束不指定、开关指定 → [原件](../../00_input/沟通记录/20260924_客户A_线束开关确认.pdf)
- [变更] 欠压保护阈值 2.8V → 2.6V，客户 9/23 邮件同意 → [ECN-003](../变更记录_ECN/ECN-003_欠压阈值调整.md)
- [打样] V1.1 板回样 5pcs，功能正常，空载电流偏高 → [打样记录](../../02_hardware/打样记录/V1.1_20260920/)
- [问题] -10℃ 下堵转保护误触发，已定位到 ADC 采样时序 → [问题-005](../问题追踪/问题-005_低温堵转误触发.md)
```

模板见 `06_management/开发日志/日志模板.md`。

好处：任何人（或 AI）想知道「这个项目怎么走到今天的」，只读这一个目录就能顺着链接查到底层证据；
而每类记录的正文仍在它该在的地方，不会被日志目录架空。

## 四、新项目怎么用

1. 整棵复制本目录，文件夹改名为项目名（`项目名` 用 ASCII 小写 + 连字符，如 `a10-cleaner`）。
2. 把 `README.md` 里的 `__PROJECT__` 换成项目名。
3. 打开 `NEW_PROJECT_CHECKLIST.md` 逐项过一遍。
4. 在**根目录** `git init` 并首次提交，先只提交空骨架，作为干净基线。
5. 在 `03_software/` 里**另外** `git init` 一个仓库管固件（做法与理由见第一节末）。

> 空目录都放了 `.gitkeep` 占位。往目录里放入实际文件后，可删掉同级 `.gitkeep`。
